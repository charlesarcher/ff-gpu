## Evidence chain (append-only)

### 2026-08-16 — Initial state
- `./build/ff_sieve --gpu-search 5 2097152` → rc=141, "Memory access fault by GPU node-1 (Agent handle ...) on address 0x7fb720001000. Reason: Page not present or supervisor privilege." (run 1 AND run 2, 0 solutions)
- Earlier `verify.sh ./build/ff_sieve --all-legs --gpu-search` claimed ALL PASS incl. 2M — **CONTRADICTION**.
- Root cause of contradiction found: `scripts/verify.sh` line 64 sets `GPU_SEARCH=1` but line 122 invokes `"$bin" "${devarg[@]}" "${PASSTHROUGH[@]}" 5 "$leg"` — **`--gpu-search` is never added to the invocation**. The flag only gates a print at line 227. So verify.sh --gpu-search actually ran CPU search. Harness bug = Bug A.
- slab_cmp ctest: 5/10 failed. Byte mismatches at non-aligned/truncated segments: value 500000 cpu=0x08 gpu=0xff; 100000 cpu=0x00 gpu=0x08; 524288 cpu=0x00 gpu=0xff; 524192 cpu=0xf8 gpu=0xff; 1200 cpu=0x82 gpu=0xff.
- Issues notepad (ff-gpu-consolidated): 2M crash hypothesis — sharded map: home=[6 11] (6 AMD + 11 NVIDIA slabs), staged=3 slabs host-staged → 15/17 slabs on-device; kernel assumes single-device contiguous d_primeMap → page fault. Launcher-level fix needed (serialize/copy distributed map, or restrict GPU search to single-device maps).

### 2026-08-16 18:43 CDT — Resume: all 4 bugs fixed and verified
Working tree (uncommitted) contained complete fixes; rebuilt (ninja: no work to do; arch objs current) and verified end-to-end.

- **Bug A — FIXED, VERIFIED.** `scripts/verify.sh` now forwards `--gpu-search` (`searcharg` array, lines ~120–127). `./scripts/verify.sh ./build/ff_sieve --all-legs --gpu-search` → header "M4 GPU-search mode (--gpu-search), all 6 legs", **ALL 6 LEGS PASS**, all byte-identical incl. 2M (71424 solutions).
- **Bug B — FIXED, VERIFIED.** True root cause: **wrong-arch kernel launch**, not sharded-map page fault (H1 rejected). Both vendor runtimes number devices from 0; the launcher's AMD-first index guess launched the gfx1201 kernel against the sm_120 device that had been allocated the map → cross-arch page fault. Fix: `GpuSearchLaunch(deviceIndex, vendor, ...)` dispatches on the caller's `vendor` string (main.cpp passes `r.devs[i].vendor`); CMake adds `AMD_SRC_HEADERS` to per-arch object DEPENDS so kernel-header edits can't leave stale arch objects linked. 2M standalone run: **rc=0**, no fault, 71424 solutions, sums strictly ascending, zero duplicates; GPU search correctly launched on device[1] (RTX 5090, vendor=nvidia).
- **Bug C — FIXED, VERIFIED.** Root cause: **test-side indexing mismatch**, not kernel (H2 rejected). GPU kernel output is segLo-RELATIVE (byte b = values [segLo+16b, segLo+16b+16)) — matching the production slab engine's per-slab local buffers — while `slab_cmp` compared it as GLOBAL-indexed (cpu/global byte at `segLo>>4+b`). Fix in `test/source/slab_cmp.cpp::compareMaps` (`cpu[startByte+b] != gpu[b]`), doc comment in `sieve_slab_kernel.cpp`, and test 8 start moved 524200→524272 (16-aligned; relative layout coincides with global only for 16-aligned starts, which the production engine guarantees). **slab_cmp now 10/10 pass** (was 5/10).
- **Bug D — FIXED, VERIFIED.** Root cause confirmed (H3): atomicAdd slot assignment → record order = arrival order, nondeterministic. Fix: kernel writes **sum-indexed slot** `pRecords[(sum-sumStart)>>1]`; caller zero-fills the full records buffer pre-launch; `GpuSearchEmit(prime, records, slotCount)` skips zero (unsolved) slots and numbers emitted solutions 1..N — deterministic, no sort. Tests updated (m4_kernel_unit, m4_order verify raw slot order instead of post-hoc sort). **m4_order: byte-identical to golden** (2359 lines, 0 mismatches), slot order "strictly ascending". **Full ctest: 5/5 pass** (incl. m4_kernel_unit 2685/2685 sampled sums matched).
